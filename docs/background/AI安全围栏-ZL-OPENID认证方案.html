ZL-OPENID 简单认证方案（D2 落地）

📌 背景：E2 结论——现有网关无鉴权能力，因此一期必须建设基础身份识别。本方案定位"简单认证"：识别调用方身份 + 白名单校验，为规则 scope（按业务方）、全链路日志与统计提供调用方标识；完整鉴权（统一认证/OAuth2/mTLS）二期演进。

一、方案总览

要素方案
身份标识请求头 ZL-OPENID：业务方编码（如 app_yl_yongying、sbzj_device、hx_core）
认证强度一期：白名单校验（编码在册即通过）＋ 可选静态密钥 ZL-API-KEY 比对（默认启用）
实现位置网关 WebFlux 链路中新增 WebFilter（非阻塞），在规则匹配/脱敏之前执行
凭据管理业务方编码→密钥映射存 Apollo（密文），网关本地缓存；密钥可轮换
失败处置缺失/非法 → 默认拒绝（401/403）；可按业务方配置为"透传+告警"（低风险场景）
输出鉴权通过后注入请求上下文：consumer（=ZL-OPENID）、安全等级；并随请求标识写入日志

二、Header 接口约定

Header类型必填示例校验规则
ZL-OPENIDString是sbzj_device非空、长度 ≤64、在白名单中（本地缓存）
ZL-API-KEYString是*zkey_xxxxxxxx与配置映射比对一致（*一期若未启用密钥校验则可不传，见 D2-2）

三、校验流程（响应式、非阻塞）

  1. 网关收到请求 → WebFilter 读取 ZL-OPENID（缺失 → 走降级/拒绝分支）；
  2. 查本地缓存白名单（Caffeine，Apollo 推送更新）：编码不存在 → 拒绝（403 + 错误码 AUTH_OPENID_INVALID）；
  3. 若启用密钥校验：比对 ZL-API-KEY 与配置值（常量时间比较），不一致 → 拒绝（401 AUTH_KEY_MISMATCH）；
  4. 通过 → 将 consumer、安全等级写入请求上下文（Reactor Context），后续规则匹配 scope 与日志模块直接读取；
  5. 为请求生成统一请求标识 request_id（与链路标识模块联动），一并入上下文。

四、与现有网关的集成要点（WebFlux / ResponseEmitter）

  • 以 WebFilter / HandlerFilterFunction 实现，全程非阻塞（不调用阻塞 IO、不用 ThreadLocal 传递业务值，用 Reactor Context）；
  • 流式请求（SSE，ResponseEmitter）同样先经过 Filter，鉴权与脱敏在流式输出前完成；
  • 白名单缓存更新走 Apollo 推送，不影响请求链路；
  • 与脱敏插件解耦：鉴权模块只产出"调用方身份 + 安全等级"，处置逻辑由规则引擎消费。

五、异常与降级

场景默认行为可配置日志记录
ZL-OPENID 缺失拒绝 401按路由/接口配置为透传+告警记录缺失、路由、时间
ZL-OPENID 不在白名单拒绝 403同上记录非法编码、来源 IP
密钥不匹配拒绝 401同上不记录密钥明文
Apollo 不可用（白名单缓存过期）按安全等级降级：拒绝（默认）或透传+告警按业务方记录降级原因

六、安全注意事项

  • 仅接受 HTTPS 传输；网关内网入口前置，Header 由网关覆盖/校验，防止下游伪造透传；
  • 密钥比对用常量时间比较，防时序侧信道；日志、监控、异常信息中禁止输出密钥明文；
  • 密钥轮换：Apollo 更新 → 双密钥窗口（新旧并行 5 分钟）→ 验证后下线旧密钥，全程告警；
  • 白名单与密钥映射属敏感配置，管理后台变更需留痕（rule_change_log 同源审计，或独立 auth_change_log）。

七、二期升级路径

  1. 一期：白名单 + 可选静态密钥（本方案）；
  2. 二期：接入统一认证体系（OAuth2 Client Credentials / 行内统一门户），ZL-OPENID 作为业务方标识保留，密钥校验升级为令牌校验；
  3. 完整授权（按接口/模型粒度）二期交付；统一流式/非流式接口一期已实现（请求统一 JSON，按 stream:true/false 以 SSE 或一次性 JSON 返回）。
