AI安全围栏建设方案（定稿版 v1.0）

版本：v1.0 定稿 ｜ 状态：已合入两轮设计评审结论与全部已确认决策（D1~D6 / E1~E3 / T1~T7）。
说明：【规划】表示二期或远期目标，一期不实现；一期范围以 1.6 节为准。

1. 背景与目标

1.1 需求背景

随着人工智能技术在金融领域的深入应用，我司各业务系统广泛对接外部AI模型以提升服务效能，随之而来的敏感数据泄露风险及合规要求却未能及时建设。因此，在开放平台建设AI安全围栏，统一管控AI调用链路，已成为保障金融业务安全、稳定、合规发展的当务之急。

1.2 名词解释

术语说明
上行链路内网相关系统通过开放平台访问外部模型的数据传输链路
下行链路外部模型执行完后响应回开放平台的数据传输链路
脱敏对敏感数据执行掩码 / 替换 / 删除等处理
处置策略（disposition）命中敏感数据后的顶层决策：拦截 / 脱敏放行 / 替换占位（二期：一致占位、返回后还原）
旁路观察（dry-run）只检测不执行处置，记录"如执行会命中什么"日志，用于验证规则准确性
同步/异步检测同步=响应返回用户前完成检测；异步=旁路检测不阻塞响应（一期下行不做，见 1.6）

1.3 主要问题

  • 上行报文中包含用户隐私数据（手机号、身份证、邮箱等）、企业内部敏感信息（API Key、内部 IP、商业数据等），缺乏统一的脱敏机制，数据直接透传至 AI 模型侧；
  • 模型返回内容缺乏检测，可能涉及脚本注入和涉政、涉黄、涉恐等违规内容（一期不做，见 1.6）。

1.6 系统设计目标与一期范围

一期范围：上行链路敏感数据完全管控（P0）+ 必要支撑。已确认决策：

1.7 合规要求（新增）

  • 适用法规：《个人信息保护法》《数据安全法》《网络安全法》《生成式人工智能服务管理暂行办法》及金融行业标准 JR/T 0197-2020《金融数据安全 数据安全分级指南》、JR/T 0171-2020《个人金融信息保护技术规范》；
  • 数据出境：外部模型供应商为字节火山方舟、阿里百炼（均国内部署，兼容 OpenAI 接口格式）——无数据出境风险；仍需向供应商确认数据留存与训练政策（不将我方数据用于模型训练、明确留存期限）；
  • 数据分级：9 类敏感信息清单（2.6）与行内数据分级（L1~L5 / C1~C3）的映射待安全合规确认后发布 v1.1；
  • 日志原则：日志中不得保存未脱敏的敏感数据明文；original_hash 仅用于比对审计。

2.5 规则模型（T2，定稿）

职责划分：disposition = 顶层处置决策；mask_strategy = 具体脱敏手法，仅在 disposition=mask_pass 时生效。

disposition一期含义mask_strategy
block✅直接拦截请求，返回错误码无需
mask_pass✅脱敏后放行mask_middle / replace / delete
replace✅替换为统一占位符 [REDACTED] 后放行无需
placeholder⏸ 二期一致占位符（跨请求稳定）字典表
restore_after_return⏸ 二期返回后还原映射表

规则 JSON 示例：

{
  "rule_id": "rule_001",
  "rule_name": "手机号脱敏",
  "match_type": "regex",
  "match_pattern": "1[3-9]\\d{9}",
  "field_path": "$.messages[*].content",
  "disposition": "mask_pass",
  "mask_strategy": "mask_middle",
  "mask_config": { "keep_prefix": 3, "mask_char": "*", "keep_suffix": 4 },
  "priority": 1,
  "enabled": true,
  "rule_version": 1,
  "scope": { "routes": ["route_ai_chat"], "consumers": ["app_system_a"], "models": ["qwen-max"] }
}

校验规则：disposition=block/replace 不允许同时配置 mask_strategy；disposition=mask_pass 必须配置 mask_strategy；非法组合拒绝保存。

3. 接口设计

3.1 ZL-OPENID 鉴权（D2）

Header类型必填示例校验
ZL-OPENIDString是sbzj_device非空、≤64 字符、在白名单
ZL-API-KEYString是*zkey_xxxx与配置比对一致（*未启用密钥校验时可缺省）

校验流程：读取 ZL-OPENID → 查白名单缓存（缺失/非法 → 拒绝 401/403，可配置透传+告警）→ 通过则注入 consumer 与安全等级到请求上下文 → 生成 request_id。完整方案见《ZL-OPENID 认证方案》。

  • DELETE /api/v1/desensitization/rules/{rule_id}
  • PATCH /api/v1/desensitization/rules/{rule_id}/status（enabled）

4. 关键方案设计

4.1 访问鉴权（ZL-OPENID）

见《ZL-OPENID 认证方案》及 3.1；WebFlux WebFilter 非阻塞实现，在规则匹配/脱敏之前执行。

4.2 上行数据脱敏链路

请求统一为 JSON（OpenAI 格式 messages[].content，含 stream:true/false）：解析 → 鉴权（ZL-OPENID）→ 规则匹配（字段路径优先+局部正则）→ 处置执行（block/mask_pass/replace）→ 报文重组 → 转发外部模型（火山/阿里，统一适配层）。转发与返回按 stream 标志分流：stream=true → WebClient 转发，响应以 SSE 流式返回调用方（ResponseEmitter/Flux 透传）；stream=false → RestTemplate 转发，一次性返回 JSON。一期响应内容仅透传（下行检测二期，含流式分片合并）。

4.3 规则存储与热加载（T1）

  1. 管理后台 CRUD → Oracle 落库（rule_version 自增）；
  2. 更新 Apollo 变更信号（version++）→ 长轮询推送；
  3. 网关拉取全量启用规则（<1000 条，毫秒级）→ 预编译正则 → 重建 Caffeine 缓存；
  4. 下一请求即生效：≤1s、无需重启。

降级：Apollo 不可用 → 用本地缓存（TTL 5 分钟，超期按业务方安全等级 reject/passthrough）；Oracle 拉取失败 → 保留旧缓存+告警；正则编译失败 → 跳过该规则+告警。

4.4 异常处理

场景处理策略影响范围
01 规则配置中心不可用本地缓存继续；缓存过期按降级策略规则更新延迟
02 报文解析失败记录告警，按降级策略（拒绝/透传）当前请求
03 规则匹配异常（正则超时）跳过该规则，记录告警当前请求该规则
04 脱敏执行异常记录告警，按降级策略当前请求
05 脱敏日志写入失败异步重试，不影响主流程日志完整性

降级模式：reject（拒绝请求，安全要求高场景）/ passthrough（透传+告警，可用性优先场景）；"提示"模式二期。

4.5 密钥管理（T4：一期暂不做）

✅ 已定：一期暂不做专门密钥管理。最小要求：模型 API Key（火山/阿里）与 ZL-API-KEY 存 Apollo（配置中心已有访问控制），网关启动加载到内存，禁止写入日志/异常信息；Key 轮换采用人工方式（更新 Apollo + 配置刷新）。正式密钥体系（AES 加密存储、KMS、自动轮换）二期建设；加密脱敏（P2）密钥体系随 KMS 一并设计。

4.6 变更三板斧（T5）

板斧一期落地
可监控水星日志统计 + 本地计数告警；JVM 走猫头鹰；Prometheus 二期接入（需技评）

可应急规则级一键停用（秒级生效）；插件级熔断（异常率超 5% 自动降级透传+告警）；规则版本回退；回滚包；恢复目标 ≤30 分钟（顺序：总开关 → 规则回退 → 插件回退包）

4.7 下行内容异步检测【规划】

一期不做（D6）。模块设计保留：异步采集、流式分片合并、内容安全检测（规则+语义）、结果反馈（3 模式）、告警复核。语义检测模型仅作为规划目标——行内资源与业务诉求未定，不设强制识别率指标；一期聚焦上行管控。
