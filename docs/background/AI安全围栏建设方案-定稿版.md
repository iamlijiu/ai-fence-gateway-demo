> **版本**：v1.0 定稿 ｜ **状态**：已合入两轮设计评审结论与全部已确认决策（D1~D6 / E1~E3 / T1~T7）

## 1. 背景与目标

### 1.1 需求背景

随着人工智能技术在金融领域的深入应用，我司各业务系统广泛对接外部AI模型以提升服务效能，随之而来的敏感数据泄露风险及合规要求却未能及时建设。因此，在开放平台建设AI安全围栏，统一管控AI调用链路，已成为保障金融业务安全、稳定、合规发展的当务之急。

### 1.2 名词解释

| 术语 | 说明 |
|---|---|
| 上行链路 | 内网相关系统通过开放平台访问外部模型的数据传输链路 |
| 下行链路 | 外部模型执行完后响应回开放平台的数据传输链路 |
| 脱敏 | 对敏感数据执行掩码 / 替换 / 删除等处理 |
| 处置策略（disposition） | 命中敏感数据后的顶层决策：拦截 / 脱敏放行 / 替换占位（二期：一致占位、返回后还原） |
| 旁路观察（dry-run） | 只检测不执行处置，记录"如执行会命中什么"日志，用于验证规则准确性 |
| 同步/异步检测 | 同步=响应返回用户前完成检测；异步=旁路检测不阻塞响应（一期下行不做，见 1.6） |

### 1.3 主要问题

- 上行报文中包含用户隐私数据（手机号、身份证、邮箱等）、企业内部敏感信息（API Key、内部 IP、商业数据等），缺乏统一的脱敏机制，数据直接透传至 AI 模型侧；
- 模型返回内容缺乏检测，可能涉及脚本注入和涉政、涉黄、涉恐等违规内容（一期不做，见 1.6）。

### 1.6 系统设计目标与一期范围

**一期范围**：上行链路敏感数据完全管控（P0）+ 必要支撑。已确认决策：

- **D1**：规则配置采用"预置规则集 + 基础 CRUD + 校验"最小形态；
- **D2**：接入鉴权一期采用 **ZL-OPENID** 简单认证（请求头识别调用方身份，白名单 + 可选静态密钥；网关原无鉴权，必须建设）；**统一流式/非流式接口一期实现**——请求报文统一 JSON（stream:true/false），网关按标志以 SSE 或一次性 JSON 返回；
- **D3**：一致占位符 / 返回后还原放二期；
- **D4**：9 类敏感信息按金融租赁行业通用做法制定标准（见 2.6）；
- **D6**：**一期不做下行内容检测**，仅作为规划目标（语义检测模型行内资源与诉求未定，不设强制指标）。

### 1.7 合规要求（新增）

- **适用法规**：《个人信息保护法》《数据安全法》《网络安全法》《生成式人工智能服务管理暂行办法》及金融行业标准 JR/T 0197-2020《金融数据安全 数据安全分级指南》、JR/T 0171-2020《个人金融信息保护技术规范》；
- **数据出境**：外部模型供应商为**字节火山方舟、阿里百炼**（均国内部署，兼容 OpenAI 接口格式）——**无数据出境风险**；仍需向供应商确认数据留存与训练政策（不将我方数据用于模型训练、明确留存期限）；
- **数据分级**：9 类敏感信息清单（2.6）与行内数据分级（L1~L5 / C1~C3）的映射待安全合规确认后发布 v1.1；
- **日志原则**：日志中不得保存未脱敏的敏感数据明文；original_hash 仅用于比对审计。

## 2. 系统设计

### 2.1 方案对比与选型

选型结论：**方案 A（现有网关集成）**，理由与演进路线保留原方案（模块化隔离，为后续拆分独立服务留路径）。

**修正（E3）**：原"无需新增基础设施"不成立——管理后台需**新建独立应用**（原有管理平台前后端一体且与网关不在同一应用），作为新增组件纳入资源变更（5.5）。

### 2.5 规则模型（T2，定稿）

**职责划分**：`disposition` = 顶层处置决策；`mask_strategy` = 具体脱敏手法，仅在 `disposition=mask_pass` 时生效。

| disposition | 一期 | 含义 | mask_strategy |
|---|---|---|---|
| `block` | ✅ | 直接拦截请求，返回错误码 | 无需 |
| `mask_pass` | ✅ | 脱敏后放行 | mask_middle / replace / delete |
| `replace` | ✅ | 替换为统一占位符 [REDACTED] 后放行 | 无需 |
| `placeholder` | ⏸ 二期 | 一致占位符（跨请求稳定） | 字典表 |
| `restore_after_return` | ⏸ 二期 | 返回后还原 | 映射表 |

规则 JSON 示例：

```json
{
  "rule_id": "rule_001",
  "rule_name": "手机号脱敏",
  "match_type": "regex",
  "match_pattern": "1[3-9]\\d{9}",
  "field_path": "$.messages[*].content",
  "disposition": "mask_pass",
  "mask_strategy": "mask_middle",
  "mask_config": { "keep_prefix": 3, "mask_char": "*", "keep_suffix": 4 },
  "priority": 1,
  "enabled": true,
  "rule_version": 1,
  "scope": { "routes": ["route_ai_chat"], "consumers": ["app_system_a"], "models": ["qwen-max"] }
}
```

校验规则：`disposition=block/replace` 不允许同时配置 mask_strategy；`disposition=mask_pass` 必须配置 mask_strategy；非法组合拒绝保存。

### 2.7 非功能需求

| 指标 | 要求 |

## 3. 接口设计

### 3.1 ZL-OPENID 鉴权（D2）

| Header | 类型 | 必填 | 示例 | 校验 |
|---|---|---|---|---|
| `ZL-OPENID` | String | 是 | `sbzj_device` | 非空、≤64 字符、在白名单 |
| `ZL-API-KEY` | String | 是* | `zkey_xxxx` | 与配置比对一致（*未启用密钥校验时可缺省） |

校验流程：读取 ZL-OPENID → 查白名单缓存（缺失/非法 → 拒绝 401/403，可配置透传+告警）→ 通过则注入 consumer 与安全等级到请求上下文 → 生成 request_id。完整方案见《ZL-OPENID 认证方案》。

### 3.2 脱敏规则管理接口

- `POST /api/v1/desensitization/rules`（含 disposition / rule_version 字段）
- `GET /api/v1/desensitization/rules?page=1&page_size=20&route=...`
- `PUT /api/v1/desensitization/rules/{rule_id}`
- `DELETE /api/v1/desensitization/rules/{rule_id}`
- `PATCH /api/v1/desensitization/rules/{rule_id}/status`（enabled）
- 管理接口鉴权：管理后台访问控制 + 操作留痕（rule_change_log）

### 3.3 统计查询接口

- `GET /api/v1/desensitization/stats?start_time=&end_time=&route=&consumer=&model=&rule_id=`（一期基础版）

### 3.4 下行检测结果反馈接口【规划】

二期定义：回调/MQ 方式异步反馈业务方（含重试、幂等、鉴权）。

## 4. 关键方案设计

### 4.1 访问鉴权（ZL-OPENID）

见《ZL-OPENID 认证方案》及 3.1；WebFlux `WebFilter` 非阻塞实现，在规则匹配/脱敏之前执行。

### 4.2 上行数据脱敏链路

请求统一为 JSON（OpenAI 格式 `messages[].content`，含 `stream:true/false`）：解析 → 鉴权（ZL-OPENID）→ 规则匹配（字段路径优先+局部正则）→ 处置执行（block/mask_pass/replace）→ 报文重组 → 转发外部模型（火山/阿里，统一适配层）。**转发与返回按 stream 标志分流**：`stream=true` → WebClient 转发，响应以 SSE 流式返回调用方（ResponseEmitter/Flux 透传）；`stream=false` → RestTemplate 转发，一次性返回 JSON。一期响应内容仅透传（下行检测二期，含流式分片合并）。

### 4.3 规则存储与热加载（T1）

1. 管理后台 CRUD → Oracle 落库（rule_version 自增）；
2. 更新 Apollo 变更信号（version++）→ 长轮询推送；
3. 网关拉取全量启用规则（<1000 条，毫秒级）→ 预编译正则 → 重建 Caffeine 缓存；
4. 下一请求即生效：**≤1s、无需重启**。

降级：Apollo 不可用 → 用本地缓存（TTL 5 分钟，超期按业务方安全等级 reject/passthrough）；Oracle 拉取失败 → 保留旧缓存+告警；正则编译失败 → 跳过该规则+告警。

### 4.4 异常处理

| 场景 | 处理策略 | 影响范围 |
|---|---|---|
| 01 规则配置中心不可用 | 本地缓存继续；缓存过期按降级策略 | 规则更新延迟 |
| 02 报文解析失败 | 记录告警，按降级策略（拒绝/透传） | 当前请求 |
| 03 规则匹配异常（正则超时） | 跳过该规则，记录告警 | 当前请求该规则 |
| 04 脱敏执行异常 | 记录告警，按降级策略 | 当前请求 |
| 05 脱敏日志写入失败 | 异步重试，不影响主流程 | 日志完整性 |

降级模式：`reject`（拒绝请求，安全要求高场景）/ `passthrough`（透传+告警，可用性优先场景）；"提示"模式二期。

### 4.5 密钥管理（T4：一期暂不做）

✅ 已定：**一期暂不做专门密钥管理**。最小要求：模型 API Key（火山/阿里）与 ZL-API-KEY 存 Apollo（配置中心已有访问控制），网关启动加载到内存，**禁止写入日志/异常信息**；Key 轮换采用人工方式（更新 Apollo + 配置刷新）。正式密钥体系（AES 加密存储、KMS、自动轮换）二期建设；加密脱敏（P2）密钥体系随 KMS 一并设计。

### 4.6 变更三板斧（T5）

| 板斧 | 一期落地 |
|---|---|
| 可监控 | 水星日志统计 + 本地计数告警；JVM 走猫头鹰；**Prometheus 二期接入（需技评）** |
| 可灰度 | 规则 scope 按业务方/路由灰度（先低风险业务方）；全局功能总开关；**旁路观察模式（dry-run）** |
| 可应急 | 规则级一键停用（秒级生效）；插件级熔断（异常率超 5% 自动降级透传+告警）；规则版本回退；回滚包；恢复目标 ≤30 分钟（顺序：总开关 → 规则回退 → 插件回退包） |

### 4.7 下行内容异步检测【规划】

一期不做（D6）。模块设计保留：异步采集、流式分片合并、内容安全检测（规则+语义）、结果反馈（3 模式）、告警复核。**语义检测模型仅作为规划目标**——行内资源与业务诉求未定，不设强制识别率指标；一期聚焦上行管控。

## 5. 资源变更

### 5.1 数据库变更（T3 定稿）

四张表（Oracle）：`desensitization_rule`（含 disposition/rule_version/gray_scope）、`desensitization_log`（含处置结果/风险等级/耗时/调用方/模型）、`violation_log`（下行违规记录，二期启用、表先建）、`rule_change_log`（规则操作审计）。索引与保留周期：日志 180 天（可归档）、违规记录 3 年、规则变更审计 3 年。完整 DDL 见《技术方案 T1~T7》T3。

### 5.2 配置变更

- Apollo 命名空间 `dsh-rule-signal`（规则变更信号，仅存版本号）；
- Apollo 密钥密文（模型 API Key、ZL-API-KEY，AES-GCM 加密）；
- ZL-OPENID 白名单与密钥映射（管理后台维护，敏感配置留痕）。

### 5.3 消息订阅变更

一期无新增；二期：下行检测任务队列（MQ）。

### 5.4 定时任务变更

一期：本地缓存 TTL 刷新守护；二期：统计聚合、违规检测重试、反馈重试。

### 5.5 其他资源变更

- **新增管理后台应用**（E3，独立部署，内网访问控制）；
- 网关插件改造（鉴权/解析/匹配/处置/降级）；
- 模型侧：申请火山方舟、阿里百炼 API Key，确认数据留存政策。

## 6. 验收与测试

### 6.1 验收标准

| 功能 | 验收标准 |
|---|---|
| 规则配置 | API 创建/修改/删除/查询；变更 ≤1s 生效；非法配置拒绝保存 |
| 掩码/替换/删除脱敏 | 示例值符合预期；非匹配内容不受影响；误修改率 ≤0.01%（每日抽检） |
| 拦截 | block 规则命中即拒绝并返回错误码 |
| ZL-OPENID 鉴权 | 白名单校验通过/拒绝符合预期；缺失/非法按配置处置 |
| 热加载 | 规则变更 ≤1s 生效、无需重启 |
| 降级 | 配置中心不可用时按降级策略执行并记录原因 |
| 日志 | 关键安全事件记录率 ≥99.99%；日志不含明文敏感数据 |

### 6.2 测试方案

- 功能测试：9 类敏感信息 × 正常/变体/伪装样例（构造测试集）；
- 性能压测：报文 10KB/100KB × 规则集 50/200 条 × 场景 QPS（设备之家 100 QPS 起步）→ 校验 2.7.1 指标；
- 回归测试：开启安全围栏前后业务接口行为对比（不影响原业务）；
- 安全对抗：变体绕过（全角/零宽字符/Base64/拼接）、Header 伪造。

### 6.3 上线流程

低风险业务方灰度（scope）→ 旁路观察（dry-run 验证规则）→ 全量；应急顺序：总开关 → 规则回退 → 插件回退包。
