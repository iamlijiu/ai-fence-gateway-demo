AI安全围栏建设方案 — 设计评审意见

  • 评审对象：《AI安全围栏建设方案 (2).md》
  • 评审范围：需求、架构、安全合规、性能可靠性、数据模型、接口设计、上线保障
  • 评审结论：有条件通过 —— 方案总体方向正确、落地性强，但存在 7 项必须解决（P0）的问题、12 项应解决（P1）的问题，建议修订后进入下一阶段。

一、总体评价

方案质量整体较高：

  • 选型对比（方案 A/B）维度全面、结论有理由、有演进路线，避免过度设计；
  • 建设目标高度指标化，具备可验收性；
  • 模块划分与组件归属清晰，异常场景枚举较全（5 类异常 + 2 种降级模式）；
  • 统一请求标识贯穿全链路、日志不存明文等设计方向正确。

但作为金融场景的安全建设方案，在合规、数据模型、上线保障三个维度存在明显缺口，且文档内部有多处指标与需求不一致，需在评审通过前解决。

二、方案亮点（无需改动）

  1. 统一请求标识（链路标识模块）：贯穿鉴权 → 匹配 → 脱敏 → 模型调用 → 下行检测 → 反馈，是全链路审计追溯的基础，设计正确。
  2. 日志不保存明文 + original_hash 的设计方向正确（但哈希方案需细化，见 P0-6）。
  3. 异步/旁路检测不阻塞响应链路：符合"控制时延、不影响原业务"的业务诉求。
  4. 规则模型设计合理：match_type / match_pattern / field_path / mask_strategy / priority / scope 组合清晰，scope 支持按路由/业务方/模型维度生效，为灰度发布留了口子。
  5. 异常降级（reject / passthrough）+ 缓存兜底思路正确。

三、必须解决（P0）

P0-1 规则存储主从关系不清，热加载机制未定义

  • 位置：2.2.3 技术选型（规则存储：Apollo，Oracle）
  • 问题：Apollo 是配置中心、Oracle 是数据库，两者职责不同。规则 CRUD 的主存储是哪个？Apollo 单配置项大小有限（百 KB 级），规则数量增长后是否还适合放 Apollo？"规则变更 ≤1 秒生效"依赖 Apollo 实时推送，但插件侧如何订阅、本地缓存如何失效、推送失败如何处理，均未描述。
  • 建议：明确"Oracle 为主存储 + 网关本地缓存 + Apollo 仅做变更通知"的读写链路，画出规则发布 → 生效的数据流；对 Apollo 容量做上限评估，超限时切换为独立规则库。

P0-2 下行异步检测的执行载体未定义，与"方案A不新增组件"矛盾

  • 位置：2.2.2 模块划分（违规内容检测 → 网关层）、1.3 系统设计目标
  • 问题：内容安全检测若含语义模型检测，CPU/内存开销大。若在网关进程内执行，会与同步脱敏链路争抢资源，冲击"吞吐量影响 ≤10%"的指标；若异步任务也在网关进程内跑，网关线程被长期占用。文档未定义检测任务的执行载体（独立 worker / 队列消费者 / 独立服务）。
  • 建议：明确检测任务运行在网关旁路的独立进程（同一代码库、独立部署，复用网关基础设施与配置中心），并定义队列消费、任务超时、重试、死信策略。这本质上是对"方案A不新增服务"的修正，需与选型结论对齐说明。

P0-3 "脱敏后放行 or 拦截"仍是开放问题（需求表中的"？？"）

  • 位置：1.2.2 诉求汇总第 2 行
  • 问题：处置策略直接影响规则模型与后续实现，目前仍是疑问。
  • 建议：明确处置策略为规则级字段（如 disposition: mask_pass / block），并给出判定原则（如：默认命中即脱敏放行；"高危数据类型 + 高安全等级业务方"组合才拦截）。该决策需业务方确认后在文档中定稿。

P0-4 合规缺口：数据出境、敏感数据分类分级、法规引用均缺失

  • 问题 1：外部 AI 模型若位于境外（或供应商在境外），即使脱敏后数据出境仍触发《数据出境安全评估办法》等要求，文档完全未提。
  • 问题 2：未引用《个人信息保护法》《数据安全法》《网络安全法》《生成式人工智能服务管理暂行办法》及金融行业数据分级标准（如 JR/T 0197），也未给出本行敏感数据分类分级清单（哪些字段属高等级数据、处置要求是什么）。
  • 建议：新增"合规要求"章节，列出适用法规与本行数据分级标准；明确外部模型供应商准入与数据出境评估结论；按数据级别映射处置策略（如最高等级数据禁止出境 → 直接拦截）。

P0-5 密钥管理缺失

  • 位置：加密脱敏（P2）、接入鉴权、外部模型调用
  • 问题：全文未提密钥管理。①加密脱敏（可逆加密）依赖密钥，密钥存哪、如何轮换？②网关转发到外部 AI 模型需持有模型侧 API Key，如何保管、防泄露？③接入鉴权凭据（若用 API Key）如何签发/吊销？
  • 建议：补充 KMS 或等价方案，明确密钥存放、轮换周期、审计要求；模型 API Key 通过密钥管理服务注入，禁止明文落库/落日志。

P0-6 数据模型缺口：缺违规记录表、缺处置结果字段、哈希方案未定义

  • 位置：5.1 数据库变更
  • 问题：
  1. 需求明确"违规记录持久化保存"，但库表只有 desensitization_rule 与 desensitization_log 两张，没有下行违规/检测结果表；
  2. desensitization_log 缺"最终处置结果"（放行/拦截/降级）、风险等级、耗时字段，与需求"记录……最终处置结果"不符；
  3. original_hash 的算法（建议 SHA-256 + 随机盐）与用途（比对审计、不可还原）未说明；手机号/身份证等低熵数据仍可被彩虹表/暴力枚举破解，"不可逆"需表述准确；
  4. desensitization_rule 无版本号/灰度字段，无法支撑"灰度发布、回滚"的 P1 功能；
  5. 未定义索引（request_id、rule_id、timestamp）与日志保留周期。
  • 建议：补充违规检测结果表（violation_log）设计；补齐日志字段；明确哈希算法与加盐策略；为规则表增加 version、gray_scope 等字段；给出索引与保留策略。

P0-7 变更三板斧薄弱，上线风险高

  • 位置：第 6 章
  • 问题："可灰度：暂无"、"可应急：只准备回退包"——该功能影响全链路（鉴权/解析/脱敏/转发），无灰度、无总开关直接全量上线风险大；仅靠回退包难以满足"故障恢复 ≤30 分钟"。
  • 建议：
  • 可灰度：利用规则 scope 按业务方/路由灰度，先灰度低风险业务方；新增功能总开关与旁路观察模式（只检测不执行脱敏、仅记录日志，验证规则准确性后再开启执行）。
  • 可应急：增加规则级一键停用、插件级熔断开关；明确回滚流程与时限。

四、应该解决（P1）

P1-1 指标矛盾与"100%"指标不可测量

  • 位置：1.3 与 2.4.1
  • 问题：①"单次规则匹配耗时"在规则管理模块处为 ≤10ms、规则匹配模块处为 ≤50ms、2.4.1 处为 ≤10ms，三处不一致；②"非敏感字段误修改率为 0""规则适用范围匹配准确率 100%""降级策略执行准确率 100%"等"100%"指标在工程上不可达成也不可测量。
  • 建议：统一耗时指标（建议单条规则匹配 ≤10ms、上行处理整体 P99 ≤50ms）；"100%"类指标改为可测量口径（如"误修改率 ≤0.01% 且每日抽检复核"、"关键事件日志记录率 ≥99.99%"），并定义统计口径（全量 vs 抽样）。

P1-2 流式（SSE）支持与统一接口的实现评估缺失

  • 位置：1.2.2（统一流式与非流式接口）、1.3 接入鉴权模块
  • 问题：现有网关对流式（SSE）的支持能力未评估；流式上行脱敏、流式响应分片合并的边界（合并窗口、结束判定、超时未闭合流如何处理）未定义。这是"设备之家"的核心诉求，却是方案中最薄弱的环节。
  • 建议：补充现有网关 SSE 能力盘点；定义分片合并策略（按句/按长度/按结束标记）、合并超时与未闭合流的兜底检测；明确流式请求的 request_id 与日志关联方式。

P1-3 脱敏导致 AI 能力降级的业务影响未评估

  • 问题：若模型需要真实手机号/身份证才能完成业务（如核身、订单查询），脱敏后模型无法处理，用户体验降级。文档只强调"不影响原业务"，未评估脱敏本身对业务效果的影响。
  • 建议：与业务方确认"需要真实数据才能完成的场景清单"；对这些场景明确策略（不调用模型/拦截/豁免），并量化影响面（涉及哪些接口、占比多少）。

P1-4 敏感数据分类分级清单缺失，"个人三要素"范围含糊

  • 位置：1.1、1.2.2
  • 问题：重点字段只有身份证号、手机号；姓名（三要素之一）、邮箱、银行卡、住址、位置、金融交易数据、企业内部数据（API Key、内部 IP、商业数据）等缺少明确清单与默认规则集。
  • 建议：新增"敏感数据分类清单"附录（数据类型 → 示例 → 默认规则 → 默认处置 → 默认优先级），作为初始规则集随方案发布。

P1-5 漏检兜底与检测准确性口径缺失

  • 位置：1.3 内容安全检测模块（识别率 ≥95%）
  • 问题：5% 漏检意味着敏感数据/违规内容外泄；"识别率 ≥95%"基于什么测试集、多大规模，未定义。
  • 建议：定义规则与语义检测的测试集与验收方法；明确漏检兜底机制（如高价值字段强制双检、抽检告警、人工复核）。

P1-6 提示词注入（Prompt Injection）未覆盖

  • 问题：上行除了敏感数据泄露，还存在对抗性输入风险（用户诱导模型泄露系统提示词、越权执行）。金融场景下这与数据泄露同级，方案未提。
  • 建议：功能全景中增加"上行提示词注入检测"（P1），明确检测方式（规则 + 语义）与处置（拦截或提示）。

P1-7 验收标准覆盖不全

  • 位置：2.3.2
  • 问题：仅"规则配置""掩码脱敏"有验收标准，替换/删除/加密、下行检测、日志审计、管理后台均无。
  • 建议：为每个 P0 功能补齐验收标准（含通过/失败判定、示例输入输出）。

P1-8 接口设计不完整

  • 位置：第 3 章
  • 问题：①缺下行检测结果反馈接口（业务方如何接收违规通知——需求明确要求"按照约定接口异步反馈"）；②缺统计接口响应结构；③管理后台接口的鉴权（谁可调用、如何鉴权）未提。
  • 建议：补充反馈接口定义（含重试、幂等、鉴权）；补齐响应结构；明确管理接口访问控制。

P1-9 管理后台是否为新增组件未明确

  • 位置：2.1.3（"无需新增基础设施"）
  • 问题：规则 CRUD（P0）与告警通知需要管理后台；若管理后台是新建 Web 应用，则与"无需新增基础设施/低运维成本"的选型依据矛盾。
  • 建议：明确管理后台复用现有平台还是新建；若新建，补充人力与部署评估。

P1-10 测试与压测方案缺失，性能数字无来源

  • 位置：2.4 非功能需求
  • 问题：50ms/10ms/吞吐 ≤10% 等数字没有来源与验证方法；无压测方案（报文大小、规则条数、并发模型、P99 口径）。
  • 建议：新增测试方案章节：功能测试、性能压测（给定报文规模与规则集规模的达标标准）、回归测试（验证"不影响原业务"）、安全测试（绕过检测的对抗用例）。

P1-11 日志量级、索引与保留周期未评估

  • 位置：5.1、日志模块
  • 问题：全链路日志 + 每次脱敏日志的数据量预估（QPS × 大小）、日志平台容量、保留周期、统计查询的索引设计均未提，直接影响"支持按维度统计"的可行性。
  • 建议：给出量级估算与保留策略；为统计查询设计表/索引或引入聚合存储。

P1-12 功能优先级与问题重要性矛盾

  • 位置：2.3.1 功能全景
  • 问题：下行内容检测与告警反馈列为 P2，但背景将"模型返回内容缺乏检测"列为核心问题之一，且 1.3 为其设定了 ≥95% 识别率的量化目标，优先级不匹配。
  • 建议：下行检测与反馈提升至 P1；统计报表（P2）与需求"支持多维度统计"对齐。

五、建议改进（P2）

  1. 格式保真脱敏（FPE）权衡：掩码会改变字段格式，可能影响模型解析；可评估格式保真脱敏（可逆）作为 P2 选项，并明确其与"不可逆"原则的取舍。
  2. original_hash 抗破解：明确加盐哈希，避免低熵数据被彩虹表还原。
  3. 重标识风险说明：脱敏 ≠ 匿名化，多次请求的脱敏数据仍可能被外部模型侧关联分析；需在方案中声明脱敏定位（去标识化而非匿名化）。
  4. 架构图补入文档：全文架构图均为飞书内链（internal-api-drive-stream.feishu.cn），评审方无法访问，需将图嵌入文档或补充文字描述。
  5. 占位符与细节清理：规则变更生效时间【1】秒、匹配耗时【10】ms 等占位数字需定稿；"7.7日"日期格式统一。
  6. 第 5.2~5.5 章补齐：配置变更（Apollo 命名空间）、消息订阅变更（MQ topic，若引入）、定时任务变更（统计聚合、违规重试、缓存刷新）、其他资源变更目前均为空。
  7. 外部模型调用环节的可观测性：模型供应商清单、模型调用日志（请求标识贯穿）、模型侧失败率/时延监控未定义。

六、待确认问题清单（可直接回填文档第 7 章"疑问"）

  1. 命中敏感信息的处置策略："脱敏后放行"与"直接拦截"的判定原则与默认值？（需业务方确认）
  2. 是否存在必须用真实数据才能完成的 AI 场景清单？这些场景如何处置（拦截/不调用/豁免）？
  3. 外部 AI 模型供应商清单与部署地域？数据是否出境？出境评估结论？
  4. 规则主存储：Apollo 还是 Oracle？规则规模上限预估？
  5. 下行检测执行载体：独立进程/服务是否可以接受（对"不新增组件"的修正）？
  6. 管理后台：复用现有平台还是新建？
  7. 违规检测的人工复核流程由哪个团队负责？复核时效要求？
  8. 日志保留周期与存储容量预算？
  9. 语义检测模型由谁提供（供应商/自研/开源）？模型迭代与误报率控制机制？
