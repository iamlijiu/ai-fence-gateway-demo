二、本轮新引入的问题（重点）

N1（P0）"返回后还原"机制——本轮最大新风险点，需补充详细设计

"返回后还原"指：请求脱敏 → 发给模型 → 模型返回后把脱敏值还原为真实值再给用户。这个机制目前只有一句话，存在 5 个必须回答的问题：

  1. 还原映射表管理：脱敏值 ↔ 原值的映射存在哪（内存/缓存/DB）？生命周期多长？模型调用超时、异步、长耗时（分钟级）时映射如何保留？内存压力（高并发 × 映射条目）如何评估？
  2. 跨会话数据泄露风险（最严重）：若模型响应中携带了非当前会话的脱敏值（多轮上下文污染、模型幻觉、多用户共享上下文），还原逻辑会把它替换成映射表中的真实值——可能把 A 用户的敏感数据还原给 B 用户。必须设计：映射表按会话/请求隔离，还原仅允许命中本会话的脱敏值，跨会话命中的脱敏值一律不还原（保持占位形式）。
  3. 流式响应还原：SSE 流式返回时逐字还原的工程实现（分片边界可能切开脱敏值），未定义。
  4. 与"日志不存明文"原则的冲突：还原映射即明文敏感数据，其存储安全、加密、销毁策略必须单独说明，否则违反 1.3 日志模块"日志中不得保存未脱敏的敏感数据明文"的设计原则。
  5. 与"拦截返回"的时序：若该响应命中违规需"拦截返回"，还原动作发生在拦截之前还是之后？拦截时映射表如何清理？需定义顺序与清理时机。

N2（P0）处置策略模型未落地：4 种处置方式无法用现有规则模型表达

  • 1.2.2 定义了 4 种处置（直接拒绝 / 脱敏放行 / 一致占位符 / 返回后还原），但：
  • 规则 JSON 示例（2.3.2）仍只有 mask_strategy（mask_middle / replace / delete / encrypt），没有 disposition 字段；
  • desensitization_rule 表同样只有 mask_strategy，"一致占位符""返回后还原"在表结构上无法表达；
  • "一致占位符"还需要一个全局一致性字典（如手机号 → PHONE_001）及其管理、安全、生命周期设计，文档未提。
  • 建议：规则模型增加 disposition（pass / block / placeholder / restore_after_return）+ 关联的占位符字典表 / 还原映射表设计；与 N1 一并补详细设计。

N3（P1）"9 类敏感信息"清单缺失

  • 1.3 规则匹配模块提到"识别身份证号、手机号等 9 类敏感信息"，但全文没有列出这 9 类。上轮已建议的"敏感数据分类清单"仍未出现。
  • 建议：明确 9 类清单（类型 → 示例 → 默认匹配规则 → 默认处置 → 默认优先级），作为初始规则集随方案发布；与处置策略（N2）联动。

N4（P1）同步检测 vs 异步检测的矛盾未解决

  • 新增了"高风险场景同步检测"和"拦截返回"，但：
  • "拦截返回"要求检测必须在响应返回用户之前完成（同步），这与"旁路/后置检测、不阻塞正常响应链路"的异步方案在机制上冲突——异步模式下内容已发出，"拦截"无意义；
  • 同步检测的时延预算（还是 50ms？）未定义；
  • "高风险场景"如何判定（按业务方 / 模型 / 内容类型 / 风险等级阈值）未定义。
  • 建议：明确双通道模型——高风险场景同步检测（预算内完成，可拦截/改写），低风险场景异步检测（仅记录/告警）；给出高风险场景的判定规则与同步检测时延指标。

N5（P1）"安全改写"（rewrite）实现未定义

  • 违规处置 3 种模式之一是"安全改写"，但：改写由谁执行（规则替换 / 调用另一个模型 / 人工）？改写内容的保真度如何保证（金融场景要求内容准确）？改写结果是否需要二次检测？改写失败（超时/异常）的兜底策略？
  • 建议：补充安全改写子方案，至少定义执行主体、改写策略、复检与失败兜底。

N6（P1）"分场景性能指标"未落地

  • 1.2.2 备注"性能指标放宽为分场景要求"，但 2.4.1 仍是统一的"≤50ms（P99）、吞吐下降 ≤10%"，没有分场景的指标表。
  • 建议：给出分场景指标表（如：设备之家 10000+/日的高并发场景 vs 内部员工问答场景，分别的时延/吞吐指标）。

N7（P1）一期范围界定存在内部矛盾

  • 1.3 说"一期暂不考虑规则配置化、多模态数据解析"，但 2.3.1 功能全景中"规则配置"是 P0，且规则管理模块在 1.3 标注为 P1——"规则配置化到底做不做、什么优先级"三处说法不一；
  • 接入鉴权模块标为 P1：鉴权是安全围栏的基础能力（"确保只有经过授权的业务系统能调用"），一期若不做，是否复用现有网关鉴权？需澄清，否则一期等于无鉴权；
  • 下行检测全部标 P1，而背景将"模型返回内容缺乏检测"列为核心问题之一——一期完全不碰下行？建议明确一期交付边界，避免范围蔓延。
  • 建议：统一 P0/P1 口径，明确一期交付清单（哪些功能随一期上线、哪些二期），并在文档中单独列一张"一期范围表"。

N8（P2）"一致占位符"的字典管理与安全

  • 一致性字典（脱敏值 → 稳定占位符）本质是伪匿名化映射表，泄露即全量泄露，属于高价值数据；其存储加密、访问控制、生命周期（何时销毁）、与还原映射（N1）的关系需一并设计。

N9（P2）降级"提示"模式未入配置表

  • 1.3 异常降级模块功能点为"拒绝请求、透传、提示"3 种，但 4.4.2 降级策略配置表只有 reject / passthrough 2 种——缺"提示"模式的配置项与行为说明。

N10（P2）资源预估表不完整

  • 5.1 资源预估表新增了 3 个场景的日调用量（设备之家 10000+ 次/日），但："预计数据库资源"列是空的；只有调用量，缺日志量级、存储、带宽预估；该量级下的全链路日志 + 脱敏日志 + 检测日志的数据量计算缺失，直接关系到日志平台容量与统计查询性能。

四、本轮结论与建议

总体：v2 的修订方向正确——处置策略从"？？"推进到 4 种模式、一期范围 P0/P1 分层、资源预估、架构图嵌入，都是实质性进步。

但：

  1. "返回后还原"与"一致占位符"是本轮引入的最大新机制，涉及映射表管理、跨会话泄露防护、流式还原、明文数据生命周期等设计点，必须补一份详细设计（N1/N2/N8）；
  2. 上轮 6/7 项 P0 未动（存储主从、检测载体、合规、密钥、表设计、三板斧），本轮新增问题都建立在这些基础上，建议先补 P0 再演进新特性；
  3. 文档内部仍有多处自相矛盾（10/50ms、规则配置 P0 vs P1、下行检测 P1 vs P2、降级 3 模式 vs 2 模式），需统一。

下一步可选（我可以直接帮你产出）：

  • A. 补《"返回后还原 / 一致占位符"详细设计》：映射表、会话隔离、生命周期、流式还原、与日志明文原则的兼容方案；
  • B. 修订规则模型：disposition 字段 + 占位符字典表 + 还原映射表 + 违规记录表（violation_log）DDL 建议；
  • C. 梳理"9 类敏感信息"分类清单与默认规则集；
  • D. 输出"一期范围表"与 P0/P1 优先级统一修正稿；
  • E. 分场景性能指标表。
