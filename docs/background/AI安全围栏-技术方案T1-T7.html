T1 规则存储与热加载

存储分层

层组件职责
主存储Oracle（desensitization_rule 表）规则数据唯一权威，管理后台 CRUD 落库
变更通知Apollo 命名空间（如 dsh-rule-signal）只存"规则版本号/变更信号"，不做规则全量（避免 Apollo 容量问题）
本地缓存网关进程内 Caffeine规则生效副本，请求匹配只读本地缓存，零网络 IO

规则发布 → 生效 数据流

  1. 管理后台新增/修改/启停规则 → 写入 Oracle（带 rule_version 自增）；
  2. 后台更新 Apollo 变更信号（version++）→ 长轮询推送；
  3. 网关收到信号 → 从 Oracle 拉取全量启用规则（量级 <1000 条，全量拉取毫秒级）→ 预编译正则 → 重建 Caffeine 缓存；
  4. 下一请求即用新规则 → ≤1 秒生效、无需重启（满足指标）。

异常降级

  • Apollo 不可用：继续使用本地缓存（含 TTL 策略，默认 5 分钟，超期未刷新则按业务方安全等级走 reject/passthrough 降级）；
  • Oracle 拉取失败：保留旧缓存 + 告警，规则更新延迟；
  • 正则预编译失败：该规则跳过 + 告警日志，不影响其他规则（异常场景 03 兜底）。

性能设计

  • 正则预编译缓存（Pattern 池），避免每次匹配重新编译；
  • 规则索引：按 route/consumer/model 分组（scope 预过滤），命中组后再逐条匹配，减少无效正则扫描；
  • 字段路径优先：先按字段路径定位，再做局部正则（避免全文正则全报文扫描），配合 T7 性能压测达标。

方案评估：是否引入 Redis（对比结论）

维度A：现状（Oracle+Apollo 信号+Caffeine）B：引入 Redis（规则快照+Pub/Sub）
新增组件无（全部为现有组件）Redis（需确认行内已有且运维成熟）
读路径本地内存，0 网络 IO（最快）本地 Caffeine + Redis 兜底
变更通知Apollo ReleaseMessage 推送（秒级，需确认客户端轮询/推送配置，默认可能 60s 轮询，不配置则"1s 生效"不成立）Redis Pub/Sub 即时广播，通道可控
多实例一致性各实例各自监听信号 → 各自拉 Oracle 全量（规则 <1000 条，毫秒级，可接受）共享一份快照，实例扩容无状态，一致窗口更小
故障面Apollo/Oracle 故障 → 本地缓存 TTL 兜底（默认 5 分钟）Redis 故障 → 本地缓存 TTL + Oracle 直查兜底（多一层依赖）
二期复用无占位符字典 / 还原映射（二期 D3）可直接复用 Redis

评估结论：

  1. 规则量 <1000 条、变更低频，性能不是引入 Redis 的理由（两方案读路径都是本地缓存）；关键在变更通知的实时性与多实例一致性；
  2. 现状方案（A）在一期默认采用，前提：① 网关实例数 ≤3~5；② 验证 Apollo 推送延迟可配置到秒级（不满足则"1s 生效"指标不成立，需改用短轮询或换通知通道）；③ 规则量 <1000 条成立；
  3. 若网关多实例（>5）或规则变更频繁、或行内 Redis 现成，引入 Redis（B）更稳：推荐形态"Oracle 主 + Redis 规则快照/Pub/Sub 信号 + 网关 Caffeine 读缓存"——网关不直接读 Redis（多一跳网络 IO 且 Redis 故障即全链路不可用），Redis 故障降级到本地缓存 + Oracle 直查；
  4. 二期占位符字典 / 还原映射若确定要共享存储，届时引入 Redis 收益最大，可作为二期决策点。

T2 规则模型（disposition 字段）

职责划分：disposition = 顶层处置决策（脱敏后放行 / 拦截 / 替换占位）；mask_strategy = 具体脱敏手法，仅在 disposition=mask_pass 时生效。解决原模型"4 种处置无法表达"的问题。

disposition一期含义mask_strategy
block✅直接拦截请求，返回错误码无需
mask_pass✅脱敏后放行mask_middle / replace / delete
replace✅替换为统一占位符（[REDACTED]）后放行无需（等价原"替换脱敏"）
placeholder⏸ 二期一致占位符（跨请求稳定，伪匿名化）字典表
restore_after_return⏸ 二期返回后还原映射表

规则 JSON 示例（更新版）

{
  "rule_id": "rule_001",
  "rule_name": "手机号脱敏",
  "match_type": "regex",
  "match_pattern": "1[3-9]\\d{9}",
  "field_path": "$.messages[*].content",   // OpenAI 兼容格式
  "disposition": "mask_pass",
  "mask_strategy": "mask_middle",
  "mask_config": { "keep_prefix": 3, "mask_char": "*", "keep_suffix": 4 },
  "priority": 1,
  "enabled": true,
  "rule_version": 1,
  "scope": { "routes": ["route_ai_chat"], "consumers": ["app_system_a"], "models": ["qwen-max"] }
}
{
  "rule_id": "rule_002",
  "rule_name": "API密钥拦截",
  "match_type": "regex",
  "match_pattern": "(sk-[A-Za-z0-9]{20,})",
  "disposition": "block",
  "priority": 0,
  "enabled": true,
  "rule_version": 1,
  "scope": { "routes": ["route_ai_chat"], "consumers": [] }
}

校验规则：disposition=block/replace 时不允许同时配置 mask_strategy（或忽略）；disposition=mask_pass 时必须配置 mask_strategy；非法组合拒绝保存（对应 2.3.2"非法配置拒绝保存"验收）。

✅ 已确认：disposition=replace 与原"替换脱敏"归并可接受（T2）

T3 数据库设计（Oracle DDL 建议）

3.1 desensitization_rule（增列：disposition / rule_version / gray_scope / 审计字段）

CREATE TABLE desensitization_rule (
  rule_id        VARCHAR2(64)   NOT NULL,
  rule_name      VARCHAR2(128)  NOT NULL,
  match_type     VARCHAR2(32)   NOT NULL,  -- regex / field_path / custom
  match_pattern  VARCHAR2(512),
  field_path     VARCHAR2(256),
  mask_strategy  VARCHAR2(32),             -- mask_middle / replace / delete（encrypt 二期）
  mask_config    CLOB,
  disposition    VARCHAR2(32)   NOT NULL,  -- mask_pass / block / replace（二期扩展）
  priority       NUMBER(5)      NOT NULL,
  enabled        NUMBER(1)      NOT NULL,
  scope          CLOB,                     -- JSON: routes/consumers/models
  rule_version   NUMBER(10)     DEFAULT 1 NOT NULL,  -- 灰度/回滚
  gray_scope     CLOB,                     -- JSON: 灰度范围（空=全量）
  created_at     TIMESTAMP      NOT NULL,
  updated_at     TIMESTAMP      NOT NULL,
  created_by     VARCHAR2(64)   NOT NULL,
  updated_by     VARCHAR2(64),
  deleted        NUMBER(1)      DEFAULT 0 NOT NULL,
  CONSTRAINT pk_des_rule PRIMARY KEY (rule_id)
);

3.2 desensitization_log（补处置结果/风险等级/耗时/模型/调用方）

CREATE TABLE desensitization_log (
  log_id             VARCHAR2(64)  NOT NULL,
  request_id         VARCHAR2(64)  NOT NULL,
  rule_id            VARCHAR2(64)  NOT NULL,
  field_path         VARCHAR2(256),
  mask_strategy      VARCHAR2(32),
  disposition        VARCHAR2(32),             -- 规则配置的处置策略
  disposition_result VARCHAR2(32)  NOT NULL,   -- 实际结果: pass/blocked/degraded/passthrough
  risk_level         VARCHAR2(16),             -- 高/中/低
  original_hash      VARCHAR2(128),            -- SHA-256(系统盐+原文)，仅比对审计
  cost_ms            NUMBER(10),
  route              VARCHAR2(128)  NOT NULL,
  consumer           VARCHAR2(128),            -- ZL-OPENID 调用方标识
  model              VARCHAR2(128),
  timestamp          TIMESTAMP      NOT NULL,
  CONSTRAINT pk_des_log PRIMARY KEY (log_id)
);
CREATE INDEX idx_des_log_req  ON desensitization_log (request_id);
CREATE INDEX idx_des_log_rt   ON desensitization_log (route, timestamp);
CREATE INDEX idx_des_log_cons ON desensitization_log (consumer, timestamp);
CREATE INDEX idx_des_log_rule ON desensitization_log (rule_id, timestamp);

3.3 violation_log（新增，下行违规记录，二期启用、表先建）

CREATE TABLE violation_log (
  violation_id    VARCHAR2(64)  NOT NULL,
  request_id      VARCHAR2(64)  NOT NULL,
  model           VARCHAR2(128),
  route           VARCHAR2(128),
  consumer        VARCHAR2(128),
  violation_type  VARCHAR2(64)  NOT NULL,  -- sensitive_word/script_injection/politics/porn/terror...
  risk_level      VARCHAR2(16)  NOT NULL,
  content_hash    VARCHAR2(128),           -- 违规内容哈希，不存明文
  hit_snippet     VARCHAR2(512),           -- 脱敏后的命中片段（限长）
  detect_mode     VARCHAR2(16),            -- rule / semantic
  feedback_status VARCHAR2(16),            -- pending / sent / failed
  created_at      TIMESTAMP     NOT NULL,
  CONSTRAINT pk_violation PRIMARY KEY (violation_id)
);
CREATE INDEX idx_viol_req  ON violation_log (request_id);
CREATE INDEX idx_viol_type ON violation_log (violation_type, created_at);

3.4 rule_change_log（新增，规则操作审计）

CREATE TABLE rule_change_log (
  change_id     VARCHAR2(64) NOT NULL,
  rule_id       VARCHAR2(64) NOT NULL,
  action        VARCHAR2(16) NOT NULL,  -- create/update/delete/enable/disable/gray/rollback
  rule_version  NUMBER(10),
  operator      VARCHAR2(64) NOT NULL,
  change_detail CLOB,                   -- 变更前后 JSON 快照
  created_at    TIMESTAMP   NOT NULL,
  CONSTRAINT pk_rule_change PRIMARY KEY (change_id)
);
CREATE INDEX idx_rule_chg ON rule_change_log (rule_id, created_at);

3.5 其他约定

  • original_hash：SHA-256(系统级固定盐 + 原值)，不可逆、仅用于"疑似值比对"审计；手机号/身份证为低熵数据，仍可被枚举破解，需结合库表访问控制与最小权限使用（声明为"去标识化辅助"，不视为绝对匿名）；
  • 保留周期：desensitization_log 180 天（可归档冷存储）；violation_log 与 rule_change_log 3 年（对应"违规记录持久化保存"与审计要求）；
  • 统计查询以 (route/consumer/model/rule + 时间) 走索引；月级聚合可引入汇总表（二期统计模块落地）。

✅ 已确认：表设计按本方案先行（T3），保留周期等后续按行内审计要求调整

T4 密钥管理（一期暂不做）

✅ 已定（延后）：一期暂不做专门密钥管理。最小要求：模型 API Key（火山/阿里）与 ZL-API-KEY 存 Apollo（配置中心已有访问控制），网关启动加载到内存，禁止写入日志/异常信息；Key 轮换人工执行（更新 Apollo + 配置刷新）。正式密钥体系（AES 加密存储、KMS、自动轮换）二期建设；加密脱敏（P2）密钥体系随 KMS 一并设计。
项方案
管理范围外部模型 API Key（火山方舟、阿里百炼）、ZL-API-KEY 静态密钥
存储Apollo 配置中心存密文（AES-256-GCM；加密主密钥经环境变量注入网关进程，不入库、不入代码库）
加载网关启动/配置刷新时解密加载到内存，模型调用从内存读取；日志/异常/监控禁止输出明文
轮换Apollo 更新 → 双密钥窗口（新旧并行 5 分钟）→ 验证新密钥后下线旧密钥，全程告警留痕
一期不引入独立 KMS 服务（评估二期接入行内密钥服务）；加密脱敏（P2）所需密钥体系随 KMS 一并设计
